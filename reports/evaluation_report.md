## A. Rules v1 vs v2

- **v1** (`RS-1`, `SD-1`): the rules evaluated in `reports/evaluation_report_v1.md`.
  Those results are frozen; the v1 rows below are recomputed by the same code with
  C1/C2 disabled, and a test checks they reproduce the frozen report byte for byte.
- **v2** (`RS-2`, `SD-2`) adds two approved changes, decided after the v1 evaluation:
  - **C1**: rightsizing goes to `NEEDS_HUMAN_REVIEW` if projected peak (2 x max CPU)
    >= 100%.
  - **C2**: shutdown goes to `NEEDS_HUMAN_REVIEW` if off-hours mean CPU > 5% (or is
    unknown).
- **C3** (relax the 10% mean cutoff) was rejected; no threshold value changed.
- The **held-out** set (29 resources, seed 2026) and its labels were committed
  *before* C1/C2 were implemented. It contains cases the checks should catch and
  cases they must not (max 45-49%, off-hours noise ~4%).

### 10. Limitations

- Scenarios and labels were written by the same author who wrote the rules, so the
  non-ambiguous cases mostly confirm that the code implements its own specification.
  The ambiguous cases are the informative part.
- 88 resources and 26 scenarios is a small, hand-designed set; per-class metrics on
  small classes (e.g. 2 NEEDS_HUMAN_REVIEW shutdown labels) are very noisy.
- CPU only: memory, disk and network effects of downsizing are not evaluated.
- Savings checks validate arithmetic against hand calculations, not real bills.
- No real AWS data was used. Real-world precision/recall is unknown.
